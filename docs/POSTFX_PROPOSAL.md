### 이 기획서가 **하지 않는** 제안

세 가지를 의도적으로 배제합니다. 각각 코드에 명시된 판단이 있고, 그 판단이 옳기 때문입니다.

**① 비네팅 단독 추가 — 배제**
[post.c](../src/post.c)가 명시합니다: *"비네팅, 통 왜곡, 색수차는 한 계열입니다. 모두 가장자리를 어둡게 하거나 휘게 하며, 나머지 없이 하나만 넣으면 선택이 아니라 실수로 읽힙니다."* 이 입장은 일관되며, 깨려면 **세 개를 한 세트로** 넣어야 합니다. 그 세트는 §3에서 하나의 선택지로만 제시합니다.

**② 디더를 우회하는 효과 — 배제**
현재 파이프라인의 순서는 `블룸 → 양자화 → 주사선`이고, 이 순서에 이유가 있습니다([post.c](../src/post.c)): *"주사선을 양자화하면 디더가 주사선 자체를 재현하는 데 동원되어 그림에 필요한 단계를 낭비합니다."* 4단계 양자화는 이 룩의 **예산**이며, 새 효과는 그 예산을 존중하거나 명시적으로 그 뒤에 놓여야 합니다.

**③ HDR / 물리 기반 렌더링 — 배제**
4단계로 양자화되는 화면에서 톤 매핑 곡선의 차이는 살아남지 못합니다. 부동소수점 프레임버퍼는 대역폭을 두 배로 쓰면서 최종 이미지에 아무것도 더하지 않습니다.

## 1. 진단 — 지금 무엇이 부족한가

현재 파이프라인은 **정적인 화면 한 장**으로서는 거의 완성되어 있습니다. 부족한 것은 세 가지이며, 전부 "화려함"보다는 **연출의 부재**입니다.

### 진단 A — 게임 상태가 화면에 반영되지 않는다

후처리가 전부 **상수**입니다. `POST_DUOTONE`, `GRAIN`, `BLOOM_AMOUNT`는 컴파일 타임 상수이고, 런타임에 바뀌는 것은 `uScan`(테스트용)과 `uTime`(그레인 시드)뿐입니다.

결과적으로 **피격당할 때, 체력이 바닥일 때, 훅으로 날아갈 때, 승리했을 때 화면이 전부 똑같습니다.** `main.c`에는 이미 `g_player.hurt`(피격 타이머), `g_player.health`, `g_weapon.hook_state`, `g_won`이 있고 전부 프레임마다 갱신되지만, 그중 어느 것도 후처리에 도달하지 않습니다.

승리 화면조차 [scene_draw_win](../src/scene.h)이 UI 패스에서 어두운 오버레이를 덧그리는 방식이며, 월드 자체는 변하지 않습니다.

### 진단 B — 광원이 있는데 빛나지 않는다

`Light` 구조체는 위치·반경·색상·밝기를 갖고([level.h](../src/level.h)의 `Light`) 셰이더가 프래그먼트마다 8개를 평가하지만, **광원 자체는 보이지 않습니다.** 천장의 조명등은 빛을 뿌리되 그 자리에 아무것도 없습니다.

블룸이 이미 있지만 `BLOOM_KNEE 0.25` 위의 픽셀만 번지므로, 밴딩된 조명(최대 0.80)은 좀처럼 무릎을 넘지 않습니다. **가장 밝은 광원조차 번지지 않습니다.**

### 진단 C — 움직임에 무게가 없다

이 게임의 정체성은 **속도**입니다 — 미트 훅이 38 m/s로 끌어당기고, 샷건 점프가 공중에서 5.5 m/s를 더하고, `MOMENTUM_DRAG_AIR`가 그 속도를 거의 온전히 유지합니다. README가 "빠른 이동이 저항 없이 계속되는 것"이 요점이라고 명시합니다.

**그런데 화면은 시속 0이나 시속 40이나 동일합니다.** 속도감을 전달하는 시각 요소가 전무합니다.

## 2. 설계 원칙

제안하는 모든 항목은 아래 네 가지를 지킵니다. 이는 제가 만든 규칙이 아니라 **이 코드베이스가 이미 따르고 있는 규칙**을 명문화한 것입니다.

**P1. 상수 하나로 완전히 꺼질 것.**
`POST_DUOTONE 0.0`이 *"수학적으로 아무 영향이 없어 이 기능이 없던 때와 정확히 동일하게 동작한다"*([post.h](../src/post.h))고 보장하는 것과 같습니다. 새 기능도 0에서 기존 화면과 픽셀 단위로 동일해야 합니다.

**P2. GLSL 상수 중복 금지.**
`POST_SUPERSAMPLE`은 C에 한 번만 정의되고 셰이더에 문자열로 삽입됩니다. 이전에 중복했다가 어긋나 *"원인을 알려 주지 않은 채 화면이 어긋난 타일로 찢어졌다"*고 기록되어 있습니다([post.h](../src/post.h)). 새 상수도 `POST_F()` 매크로를 통과해야 합니다.

**P3. 헤드리스로 검증 가능할 것.**
`posttest.exe`가 이미 슈퍼샘플 평균과 주사선 세기를 측정합니다. 주사선을 *"같은 프레임을 켜고/끄고 비교"*해야만 측정 가능했다는 기록([post.c](../src/post.c))처럼, 새 효과도 **토글 가능한 유니폼**으로 만들어 차분 측정이 되게 합니다.

**P4. 패스 경계를 존중할 것.**
월드는 `post_end` 이전, UI는 이후. `DIAG_WANT_WORLD_PASS`가 이를 기계적으로 감시합니다.

### 🥇 트랙 1 — 화면을 게임 상태에 연결한다 (`post_set_mood`)

**진단 A 해결. 이 기획서에서 가장 효과가 큰 항목입니다.**

새 효과를 거의 만들지 않고, **이미 있는 것들을 게임 상태로 구동**합니다.

#### 인터페이스

```c
/* post.h */
typedef struct {
    float hurt;      /* 0..1 — 피격 직후 1, 감쇠 */
    float low_hp;    /* 0..1 — 체력이 낮을수록 1 */
    float speed;     /* 0..1 — 이동 속도 / 기준 속도 */
    float win;       /* 0..1 — 승리 연출 진행도 */
} PostMood;

void post_set_mood(const PostMood *m);
```

`main.c`가 프레임마다 한 번 호출합니다. 값은 전부 이미 존재합니다:

```c
PostMood mood = {
    .hurt   = g_player.hurt,                                  /* 이미 있음 */
    .low_hp = 1.0f - (float)g_player.health / PLAYER_MAX_HP,  /* 이미 있음 */
    .speed  = v3len(g_player.vel) / MOOD_SPEED_REF,           /* 이미 있음 */
    .win    = g_won ? win_fade : 0.0f
};
post_set_mood(&mood);
```

#### 각 값이 하는 일

| 입력 | 시각적 결과 | 구현 |
|---|---|---|
| `hurt` | 잉크가 순간적으로 붉게 물듦 + 그레인 급증 | 듀오톤 잉크색을 붉은 쪽으로 lerp, `GRAIN × (1 + 3·hurt)` |
| `low_hp` | 화면이 서서히 탈색되고 그레인이 상주 | `POST_DUOTONE`를 `low_hp × 0.6`까지 상승 |
| `speed` | 주사선이 깊어지고 브리딩이 강해짐 | `uScan × (1 + 0.4·speed)` |
| `win` | 종이색으로 서서히 표백 | 듀오톤을 1.0으로, 종이색을 밝은 쪽으로 |

**`low_hp`가 듀오톤을 쓰는 것이 이 트랙의 핵심입니다.** `POST_DUOTONE`은 이미 구현되어 있지만 기본값 0으로 **한 번도 쓰이지 않고 있습니다.** [post.h](../src/post.h)이 *"0.7 부근에서는 잉크가 화면을 지배하면서도 재질 고유의 색이 희미하게 남는다"*고 기록한 그 값을, 죽어 갈 때 도달하는 상태로 쓰는 것입니다. 색이 빠지면서 세상이 흑백에 가까워지는 것은 **설명이 필요 없는 연출**입니다.

#### 왜 이것이 1순위인가

- **새 셰이더 코드가 거의 없습니다.** 상수 4개를 유니폼으로 승격하고 곱셈 몇 개를 더하는 것이 전부입니다.
- **P1을 자연스럽게 만족합니다.** `PostMood`가 전부 0이면 현재 화면과 동일합니다.
- **P3을 자연스럽게 만족합니다.** `posttest`가 mood를 설정하고 프레임을 렌더해 밝기·채도 변화를 측정할 수 있습니다. 이것이 주사선 측정에 쓴 것과 정확히 같은 차분 기법입니다.
- 이 게임에는 **이미 사망 연출이 없습니다** — 체력이 0이 되어도 화면이 변하지 않습니다. `low_hp`는 그 공백을 메웁니다.

**비용:** 셰이더 유니폼 4개, GLSL 약 15줄, C 약 40줄. `.rdata` 증가 ~600바이트 추정.
**리스크:** 낮음. 기존 경로를 건드리지 않습니다.

### 🥈 트랙 2 — 광원을 보이게 한다 (발광체 + 볼류메트릭 샤프트)

**진단 B 해결.**

#### 2-A. 광원 스프라이트 (필수 선행)

각 `Light`에 카메라를 향하는 가산 블렌드 쿼드를 그립니다. **새 코드가 거의 필요 없습니다** — `scene_draw_shots`가 몬스터 발사체에 쓰는 "회전시킨 사각형 여러 장을 가산 합성한 로제트" 관용구가 그대로 적용됩니다([scene.h](../src/scene.h)). 텍스처도 새 지오메트리 헬퍼도 필요 없습니다.

이것만으로 블룸이 비로소 작동합니다. 발광체는 휘도 1.0 부근이므로 `BLOOM_KNEE 0.25`를 확실히 넘고, **이미 구현된 블룸이 처음으로 제 일을 하게 됩니다.**

#### 2-B. 볼류메트릭 라이트 샤프트 (선택)

레디얼 블러 방식을 제안합니다. 화면 공간에서 광원 위치로부터 방사형으로 샘플을 모아 밝은 부분만 누적하는 고전적 기법이며, 이 파이프라인에 잘 맞는 이유가 셋 있습니다:

1. **오프스크린 해상도가 낮습니다.** 640×360에서 12탭 레디얼 블러는 1920×1080에서의 같은 작업보다 9배 저렴합니다. 저해상도 렌더링이 *"비용 없이 얻는 유일한 최적화"*([post.h](../src/post.h))라고 기록된 그 이점이 여기서 다시 발휘됩니다.
2. **디더가 뒤에 옵니다.** 샤프트를 양자화 이전에 더하면 블룸과 마찬가지로 디더가 이를 스티플로 해상하며, 이는 부드러운 그라데이션보다 이 룩에 훨씬 잘 맞습니다.
3. **깊이 버퍼가 이미 있습니다.** FBO에 깊이 첨부물이 있으므로 차폐 판정에 추가 렌더 타깃이 필요 없습니다.

**⚠️ 정직한 유보:** 화면 밖 광원은 레디얼 블러로 처리되지 않고, 광원이 화면 가장자리를 넘나들 때 샤프트가 튈 수 있습니다. 이는 이 기법의 알려진 한계입니다. 2-A만으로도 진단 B의 대부분이 해소되므로, **2-A를 먼저 넣고 실제 화면을 본 뒤 2-B를 판단**할 것을 권합니다.

**비용:** 2-A는 낮음(약 60줄, 기존 패턴 재사용). 2-B는 중간(셰이더 패스 1개 추가).

### 🥉 트랙 3 — 속도에 무게를 준다

**진단 C 해결.**

트랙 1의 `speed` 입력을 받아 세 가지를 구동합니다:

| 요소 | 동작 | 근거 |
|---|---|---|
| **방사형 모션 블러** | 화면 가장자리에서만, 이동 방향 기준 | 중앙을 건드리지 않으므로 조준이 흐려지지 않음 |
| **FOV 팽창** | `WORLD_FOV`를 최대 +8% | 고전적이고 즉각적인 속도 신호 |
| **훅 견인 중 채도 상승** | 듀오톤을 음수 방향으로 (색이 강해짐) | 견인이 "특별한 상태"임을 알림 |

FOV 팽창은 후처리가 아니라 카메라이므로 [scene.c](../src/scene.c)의 `mat4_perspective` 인자만 바뀝니다 — 가장 저렴하면서 가장 잘 통하는 항목입니다.

**⚠️ 유보:** 모션 블러는 **디더와 상성이 나쁠 수 있습니다.** 정렬된 Bayer 패턴을 방사형으로 문지르면 패턴이 뭉개져 노이즈로 읽힐 위험이 있습니다. 반드시 **양자화 이전**에 적용해야 하며, `dithershot.exe`로 실제 화면을 확인하기 전까지는 이 항목을 확정하지 마십시오. FOV 팽창만으로도 상당 부분 해결됩니다.

**비용:** FOV는 낮음(3줄). 모션 블러는 중간이며 검증 필요.

---

### 트랙 4 — CRT 광학 세트 (선택, 전부 아니면 전무)

[post.c](../src/post.c)가 배제한 세 가지를 **한 세트로** 넣는 선택지입니다:

- 통 왜곡 (barrel distortion)
- 색수차 (chromatic aberration) — 가장자리에서만
- 비네팅

세 개를 함께 넣으면 코드가 지적한 *"하나만 취하면 실수로 읽힌다"*는 문제가 해소되며, 화면이 브라운관 유리 안에 들어간 것처럼 보입니다.

**⚠️ 이것은 취향의 문제이며 기술적 개선이 아닙니다.** 현재의 "빼는 것도 일관된 입장"이라는 판단은 여전히 유효합니다. 통 왜곡은 정수 배율 확대의 이점을 일부 훼손하며(픽셀 격자가 가장자리에서 휘어집니다), 이는 `POST_HEIGHT` 문서가 공들여 방지한 픽셀 크리프와 같은 계열의 문제입니다.

**권고: 트랙 1~3을 먼저 적용하고, 그 결과를 본 뒤에만 검토하십시오.**

## 4. 성능 예산

### 현재 측정치

`levelbench` 기준 CPU 측 시뮬레이션은 프레임당 1 ms 미만입니다(캡 부하에서도 0.84 ms). **병목은 CPU가 아니라 픽셀 채우기이며**, 후처리 제안은 전부 GPU 쪽입니다.

### 오프스크린 해상도가 만드는 여유

```
창          1280 × 720   = 921,600 픽셀
오프스크린    640 × 360   = 230,400 픽셀  (1/4)
슈퍼샘플 2x  1280 × 720   = 921,600 픽셀  (렌더 대상)
```

후처리 셰이더는 **출력 픽셀당 한 번** 실행되지만, 새로 제안하는 효과 대부분은 오프스크린 해상도에서 동작합니다. 12탭 레디얼 블러를 640×360에서 수행하는 비용은 1280×720에서 3탭을 수행하는 것과 비슷합니다.

### 트랙별 추정 비용

| 트랙 | GPU 추가 비용 | 바이너리 |
|---|---|---|
| 1. Mood | 무시 가능 (곱셈 몇 개) | ~600 B |
| 2-A. 발광체 | 드로우 콜 광원당 1회, 최대 8회 | ~400 B |
| 2-B. 샤프트 | 오프스크린 12탭 1패스 | ~800 B |
| 3. FOV | 0 | ~100 B |
| 3. 모션 블러 | 오프스크린 6탭 | ~500 B |
| 4. CRT 광학 | 왜곡 UV 계산 + 3탭 | ~700 B |
| **합계** | | **~3.1 KB** |

**바이너리 예산 대비 0.2%입니다.** 1,341,440 바이트가 남아 있으므로 크기는 이 기획서에서 제약이 아닙니다. 제약은 오직 **룩의 일관성**입니다.

## 5. 검증 계획

기존 도구가 이미 충분합니다. 새 하네스는 필요 없습니다.

### `posttest.exe` 확장

현재 10개 검사를 수행하며, 차분 측정 기법이 확립되어 있습니다. 추가할 검사:

```
  mood가 0이면 프레임이 이전과 픽셀 단위로 동일하다        ← P1 강제
  hurt=1이 프레임의 적색 성분을 올린다
  low_hp=1이 채도를 낮춘다
  speed=1이 주사선을 깊게 한다
  발광체가 블룸 무릎을 넘긴다                              ← 진단 B가 해결됐음을 증명
```

**첫 번째 검사가 가장 중요합니다.** `PostMood`가 전부 0일 때 기존 프레임과 바이트 단위로 같아야 한다는 것은 P1의 기계적 강제이며, 이 프로젝트가 `_Static_assert`로 계약을 강제해 온 방식과 같은 정신입니다.

### `dithershot.exe`

이미 실제 레벨을 후처리를 거쳐 PNG로 씁니다. 룩 판단은 반드시 이 도구로 하십시오 — README가 기록한 교훈이 있습니다: *"~40px 효과는 축소된 1280×720 스크린샷에서 보이지 않습니다. 효과가 망가졌다고 결론 내리기 전에 잘라서 확대하십시오."*

mood 값을 인자로 받도록 확장하면 `dithershot arena -mood hurt=1` 같은 형태로 각 상태의 화면을 비교할 수 있습니다.

## 7. 종합 판단

이 프로젝트의 후처리는 **효과가 부족한 것이 아니라 연결이 부족합니다.**

듀오톤, 블룸, 브리딩, 주사선, 그레인이 전부 구현되어 있고 각각의 설계 근거가 꼼꼼히 문서화되어 있습니다. 그런데 `POST_DUOTONE`은 0으로 꺼져 있고, 블룸은 무릎을 넘는 픽셀이 없어 작동하지 않으며, 모든 값이 컴파일 타임 상수라 게임에서 무슨 일이 일어나든 화면은 동일합니다.

**따라서 가장 큰 효과는 새 효과를 만드는 데서 나오지 않습니다.** 이미 있는 것을 게임 상태에 연결하고(트랙 1), 이미 있는 블룸이 작동할 대상을 만들어 주는 것(트랙 2-A)입니다. 이 둘만으로 진단 A와 B가 해소되며, 둘 다 새 셰이더 패스를 추가하지 않습니다.

바이너리 예산은 제약이 아닙니다(0.2% 사용). 실제 제약은 **4단계 양자화**이며, 그것을 존중하지 않는 효과 — 부드러운 그라데이션에 의존하는 모든 것 — 는 이 화면에서 살아남지 못합니다. 이것이 트랙 4를 마지막에 두고 트랙 3의 모션 블러에 유보를 단 이유입니다.
